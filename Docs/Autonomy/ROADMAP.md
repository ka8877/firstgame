이번 초기 설정 이후 **G1**부터 이어간다. 제품을 처음부터 다시 만들지 않는다. 장기 방향은 [CHARTER.md](CHARTER.md), 현재 사실은 [STATE.json](STATE.json)을 따른다.

## 회차 운영

초기 배분은 **Gospel → Gospel → Cards**다. 초기 설정·검사만 한 회차는 게임 개선 횟수로 세지 않는다. 긴급 오류/저장/배포 복구와 미완료 진행 작업이 우선이다. 회차마다 완료 조건을 갖춘1~3개 작업만 선택하고, 실패 원인이 같으면 재시도는2번까지다. 진행한 척하기 위한 변경은 하지 않는다.

단일 명령 묶음은 최대2,700초(45분)다. 이 값은 이번 운영 기본값이며 자동으로 늘리지 않는다. `run`은 자식 프로세스 그룹의 시간을 강제한다. 대화형 에이전트 전체의 시간/모델 사용량, 클라우드 수명, 예약 횟수는 현재 도구가 강제하지 못하므로 실행기 설정이 별도로 필요하다. 한도 도달 시 미완료 소스/실패/재개점을 작업 브랜치와 STATE에 남기고 정상 공개판을 유지한다.

## G1 · 열두 살 여정의 현장 대화와 만남 안내 — 다음 제품 회차

대표 구간은 기존 `nazareth-departure` → `nazareth-return`의7사건이다. 요셉→마리아/샘→성전→선생들→부모→귀향을 플레이한다. **5~10분은 목표이며 아직 측정한 분량이 아니다.** 강제 대기나 대사 페이지만 늘려서 맞추지 않는다.

선정 작업과 완료 조건:

1. 기존 실행기의 **출력 경로/회차 ID만 최소 매개변수화**해 새 소스·검증 입력을 고정한다. 과거 Nativity canonical 원본/카운트를 덮거나 검증 조건을 약화하지 않는다. 용량/디스크/라이선스/실행자 확인도 먼저 한다.
2. 탄생51화면의 삽화 도입은 유지한다. **필드 NPC 대화는 현재 장소·인물을 보이는 방식**으로 전환한다. 인용/요약/극화 구분·장절·음성 중단/duck·기존 UI 입력/저장 호환을 유지한다.
3. 요셉→마리아→성전으로 이어지는 **방향·거리·상호작용 가능 상태**를 작은 HUD에서 명확하게 표시한다. 새 세계관/장르/대형 자산을 추가하지 않는다.

완료 흐름: 새 여정/기존 저장 시작 → 실제 이동·세 만남 → 첫 필드 본문 획득 → 성경에 해당 면 기록 → 저장 → 브라우저 완전 재접속 → 같은 위치/대화 이어하기. 미발견 제목/본문과 미래 장면이 새지 않아야 한다. 다른 게임의 마지막 정상 산출물은 그대로 유지한다.

검증: 관련 Core의23사건/19본문·옛 JSON·세부 대화 커서·중복 획득/숨김 회귀, Unity 컴파일/Native의 대화 중 이동/콜백/음성 취소, 실제 새 Web PC+터치의 입력/저장/reload·오류/에셋 누락·인접 화면 검토. 같은 위치·줌·해상도·방향에서 요셉/우물/성전의 전후 원본과 이동/대화 전환을 비교한다. 이동·읽기·입력 시간을 나눠 실제 분량을 기록한다. 구현 소스와 빌드 소스가 달라지면 영향 범위 재검증 후 기존 Pages에 배포하고 공개판을 다시 검사한다.

## G2 · 같은 대표 구간의 인물·장소 연결

문제 근거: `GospelPilgrimageApp.RefreshNpc`가 사건마다 기존 NPC를 제거해 현재 한 명만 생성한다. Actor의 NPC는 정지 프레임 위주여서 플레이어 보행과 차이가 크다. 확인 없이 전체 시스템을 바꾸지 않는다.

G1을 마친 뒤1~3개 작업을 선정한다. 인물이 사건 전환 때 갑자기 사라지는 부분을 줄이고, 소년 예수의 얼굴/손/실루엣·네 방향 일관성·발 접지·정지/회전/대화 복귀를 같은 장면에서 개선한다. 큰 그림이 필요하면 아래 용량 조사 뒤 직접 제작/허가된 자산으로 한다. 기존 원본 PNG·GUID·atlas layout/32프레임 계약을 보존한다.

아트 기준은 현재 회화형 인물+자유 XZ 공간을 유지한다. 숲/샘/성전마다 빛·재질·전경/중경/원경이 장소에 맞아야 한다. 고정 비교 지점은 요셉 앞, 마리아/우물, 성전 회랑이다. 정지/출발/정지/180도 회전/대화 진입·복귀를 확인한다. 블룸만 더한 결과나 자체 점수를 사용자 미술 승인/Ori 수준으로 표시하지 않는다. 다음 장소에서도 이 기준을 재사용한다.

## 대형 확장 전 용량·권리 선행 작업

현재 실제 stage15,413파일 **981,781,001B**, decimal1GB 여유18,218,999B다. 카드 JPEG749,704,026B/카드 Build112,408,306B/Gospel Build109,611,673B/스트리밍 오디오5,711,105B. 동일 SHA 중복은 notice류 최대31,622B이고 카드 JPEG 중복은 없다. 기존 JPEG는 이미 quality88 최적화, gzip level9 후보 절감0B였다. 단순 중복/지연 로딩/재압축으로 충분히 줄었다고 약속하지 않는다.

먼저 기존 BuildReport와 Resources 참조에서 **미사용 포함물**을 입증한다. 원본/GUID와 복구 ledger를 보존하며 기존 Gospel 격리 방식을 참고해 시험 빌드한다. 채택하려면 모든 현재 장면·도감15,350개·기존 PNG 카드/폴백·음성·글꼴·저장·픽셀 품질을 검증하고 전체 사이트를 다시 잰다. 그림을 저화질로 바꾸거나 오디오 포맷 한쪽을 임의 삭제하지 않는다. 충분히 줄지 않으면 소스 저장소 분리와 별개인 자산 호스팅 대안을 비교만 하며 새 유료 서비스/저장소는 만들지 않는다. 다음 사이트 예산은 기존985,000,000B 이하를 유지하고 자동으로 올리지 않는다.

현재 카드 자산의 포괄 재배포 허가는 확인되지 않았다(`Docs/ClassicCardArt.md`, selection.json). 기존 공개본을 허가 확인 완료라고 표시하지 않는다. **신규 공개 자산**은 직접 제작 또는 허가 확인이 선행된다. 미확인 신규 자산은 보류하고 규칙/저장/도구/기존 UI 작업은 계속한다.

## 현재 도구와 실행 진입

Unity6000.3.26f1, .NET8.0.426, Chromium과 모듈은 이미 설치돼 있다. 설치/라이선스/비밀값을 새로 만들거나 읽지 말고 매 회차 `Tools/Environment/check-runtime.py`와 실제 idle 상태를 확인한다. CLI 미로그인과 Editor 라이선스 유효 여부는 다르다. 제한된 실행에서 기존 Unity/NSS 저장소 접근이 거부되면 정확한 실패를 남기고 지원되는 좁은 실행 권한을 사용하며 HOME/프록시/TLS 검증을 바꾸지 않는다.

현재 검증 도구는 `run-nativity-core.py`, `nativity-task.sh`, `run-nativity-native.py`, `nativity-web-smoke.py`, `stage-nativity.py`, `verify-nativity-public.py`, `summarize-nativity-release.py`다. 새 경로·개정·명시 plan/profile을 지정하도록 최소 보완 후 사용한다. 특히 Web smoke의 기본값은 과거판이므로 기본값으로 새 통과를 만들지 않는다. 과거 결과를 새 검사로 대신하지 않는다.

단일 명령을 실행기로 감싸는 예(고유 run-id/경로 사용):

```sh
python3 Tools/Autonomy/cycle_guard.py run --record Artifacts/Validation/Autonomy/preflight-001/lease.json --run-id preflight-001 --timeout-seconds 240 -- python3 Tools/Environment/check-runtime.py
```

대화형 회차는 `acquire --record <고유 경로> --run-id <고유 ID>` 후 각 실행/통합 전 `check --record <같은 경로>`, 종료 때 `release --record <같은 경로>`다. 이미 취득한 동안 중첩 `run`을 시작하지 않는다. 원격 생성은 원자적이고 삭제는 자기 SHA에 한정한 CAS다. 다른 소유자/불명확한 권한/만료 잠금이면 건너뛰며 대기 작업을 쌓지 않는다. 소유 기록을 잃거나 종료된 실행의 잠금이 남으면 먼저 실제 실행/기록을 확인한다. 시간 경과만으로 타인 잠금을 지우지 않는다.

기존 Pages의 `concurrency: pages`, publishReady/전체 SHA/LFS 포인터 검사는 유지한다. 새 guard branch만 실제 제품 코드가 없는 조정용 ref로 분리하고, 실제 소스 브랜치의 기존 Core 검사와 새 guard15회귀를 계속 실행한다.

## 반복 실행의 최초 설정

현재 노출된 도구에는 예약/목표 실행 생성 API가 없고, 저장소에는 Unity 예약/self-hosted workflow가 없다. 기존 GitHub-hosted Core/Pages runner는 이 클라우드의 Unity·라이선스·/tmp를 공유하지 않는다. 따라서 **예약 개발은 아직 설정/검증되지 않았다**.

사용자가 앞으로 예약 실행을 만들 때 `ka8877/firstgame`와 **같은 관리형 Unity 환경**을 연결하고, 시작 지시를 “루트 AGENTS와 Docs/Autonomy/STATE.json을 읽고 미완료 작업부터 재개”로 지정해야 한다. 최초 실행은 실제 환경/라이선스/도구/Git/공통잠금이 확인돼야 한다. 실행기가 해당 환경 연결·시간/사용량 제한을 제공하지 않으면 자동 개발이 가능하다고 표시하지 않고 현재 대화에서의 자율 작업만 계속한다. 새 유료 runner나 서버를 대신 만들지 않는다.
