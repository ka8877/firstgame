너는 이 프로젝트의 Unity 테크리드이자 게임 개발 에이전트다.

나는 두 개의 고품질 싱글 플레이 게임을 개발하려고 한다.
아래에 정한 기술과 방향을 기준으로 실제 개발을 시작해라.
계획만 제시하고 끝내지 말고, 환경 확인 → 프로젝트 구성 → 첫 플레이 구간 구현 → 실행 검증까지 진행해라.

이번 목표는 두 게임의 정식 개발 기반과 짧지만 완결된 첫 구간을 만드는 것이다. 이후 내가 플레이하며 확인한 결과를 바탕으로 기능과 콘텐츠를 확장한다.

# 1. 확정된 기술과 개발 방향

공통 기술:
- Unity 6.3 LTS.
- 설치 시 6000.3 계열의 사용 가능한 안정 패치와 패키지 호환성을 확인하고, 선택한 정확한 버전을 기록·고정한다.
- C#.
- Universal Render Pipeline, URP.
- 게임 UI는 uGUI와 TextMeshPro.
- 입력은 Unity Input System.
- 카메라는 Cinemachine.
- 짧은 장면 연출은 Timeline.
- 서사게임의 대사와 선택 분기는 공식 Ink Unity Integration.
- 캐릭터·배경 모델의 제작과 수정은 Blender를 활용한다.
- Windows PC를 주 개발 대상으로 삼고 웹 체험판도 함께 빌드한다.
- 두 게임은 각각 독립적으로 실행·배포할 수 있는 Unity 프로젝트로 만든다.

기술 선택을 다시 묻지 말고 이 구성으로 진행한다.
이전에 만든 웹 시제품이 있다면 원화·분위기·화면 구성의 참고 자료로 활용한다. 본 게임 구현은 Unity 프로젝트에서 진행한다.

# 2. 먼저 개발 환경을 확인하고 준비해라

현재 운영체제, 작업 폴더, Git, Unity Hub 또는 Unity CLI, 설치된 에디터, 빌드 모듈, Codex의 Unity 연결 상태를 확인한다.

Unity 공식 Codex 플러그인이 없다면 현재 공식 설치 방법을 확인하여 설치한다. 현재 공식 CLI 설치 명령은 다음과 같다.

codex plugin marketplace add Unity-Technologies/unity-agent-plugin
codex plugin add unity@unity-agent-plugin
codex plugin list

Unity CLI와 Pipeline을 사용할 수 있다면 프로젝트를 에디터에서 연 뒤 연결을 검증한다.

unity auth login
unity pipeline install
unity pipeline list
unity command

Unity CLI는 실험적 기능임을 고려하고, 문제가 생기면 지원되는 에디터 스크립트와 배치 빌드 경로로 가능한 작업을 계속한다.

실제로 계정 로그인, 라이선스 활성화, 권한 승인 또는 결제가 필요할 때는 필요한 사용자 조치를 정확히 알려라. 그동안 가능한 프로젝트 준비 작업은 진행한다.

설치된 패키지의 공식 문서와 실제 API를 확인한다. 존재하지 않는 명령이나 오래된 예제 코드를 추정해서 사용하지 않는다.

# 3. 프로젝트 구조와 작업 방식

하나의 작업 공간 안에 다음을 구성한다.

- Games/FantasyCards: 카드게임 Unity 프로젝트.
- Games/PathOfDawn: 예수님 게임 Unity 프로젝트.
- ReferencePrototype: 기존 시제품과 참고 자료.
- Docs: 게임 설계, 아트 기준, 작업 목록, 실행·검증 기록.

현재 폴더의 ZIP이나 기존 프로젝트에서 카드 일러스트, 예수님 컨셉 원화, 3D 모델, 화면 자료를 찾아 참고한다. 기존 파일은 보존하고 필요한 에셋을 가져온다.

Git으로 변경을 관리한다.
Unity의 .meta 파일은 에셋과 함께 관리하고, 생성되는 캐시와 임시 빌드 파일은 제외한다.
큰 바이너리 에셋은 Git LFS 사용을 검토하여 구성한다.

루트와 각 게임에 AGENTS.md를 작성한다. 다음 내용을 포함한다.
- 게임의 방향과 현재 구현 범위.
- 폴더별 책임.
- 사용하는 엔진과 패키지 버전.
- 실행·빌드·검증 방법.
- 현재 아트 기준과 임시 에셋 목록.
- 다음 작업과 완료 조건.

각 게임의 코드에서 규칙·진행 상태, 화면, 콘텐츠 데이터, 저장 처리를 분리한다.
ScriptableObject는 카드나 캐릭터 등의 제작용 데이터에 사용하고, 실행 중 바뀌는 상태는 별도 객체로 관리한다.
저장되는 콘텐츠에는 안정적인 ID를 부여한다.

병렬 작업이 가능하면 코드·콘텐츠·검토를 나눠 진행하되, 같은 씬이나 프리팹을 여러 작업이 동시에 수정하지 않도록 한다.

# 4. 게임 A: 별빛의 서약

## 목표

옛 판타지마스터즈 1에 가까운 핵심 플레이 감각을 가진 싱글 판타지 카드게임을 만든다.

화면은 고품질 2D 카드 일러스트와 3D 전장을 결합한 2.5D로 만든다.
아름다운 카드 원화, 카드 수집과 덱 구성, 유닛 배치, 공방의 판단, 코인 판정의 긴장감을 중심으로 한다.

기존 웹 시제품의 즉발 공격·방어·회복 카드 전투는 참고용이다.
이번에는 아래의 전장 중심 전투 구조를 구현한다.

카드 이름, 원화, 캐릭터, 설명, 게임 로고와 UI 표현은 우리 프로젝트의 오리지널로 제작한다.

## 전투 방향

첫 전투에서 다음 요소가 실제로 작동해야 한다.

1. 지형을 전개해 속성 자원과 카드 운용 기반을 확보한다.
2. 소환한 유닛은 전장에 남아 다음 행동과 전투에 영향을 준다.
3. 유닛의 배치와 공격·방어 참여를 선택한다.
4. 공격 준비와 방어 대응이 구분되어 양쪽의 판단이 결과에 영향을 준다.
5. 코인 판정이 능력치 또는 효과에 변수를 만든다.
6. 마법과 장비를 조합해 유닛과 전투 결과에 영향을 준다.
7. 지형 비중과 유닛·마법·장비의 조합을 고려해 덱을 구성한다.

원작 판마1의 확인 가능한 가이드나 플레이 자료를 짧게 조사하고 Rules.md를 작성한다.
확인한 원작 규칙과 이번 프로젝트의 설계값을 구분한다.
판마2의 규칙을 판마1의 규칙으로 혼용하지 않는다.

확인되지 않은 세부 수치는 v0.1 설계 가정으로 기록하고 구현을 진행한다.
덱 장수, 손패와 전장 한도, 지형 설치와 자원 처리, 승리 조건, 효과와 코인 판정 순서는 RuleSet으로 조정할 수 있게 구성한다.

## 첫 콘텐츠 범위

- 속성 두 종류.
- 카드 정의 16종: 지형 4종, 유닛 6종, 마법 3종, 장비 3종.
- 카드 정의의 종류 수와 실제 덱의 장수를 구분한다.
- 플레이어 기본 덱 하나.
- AI 상대 덱 하나.
- 튜토리얼을 겸한 전투 하나.
- 시작 화면, 카드 상세 보기, 기본 덱 확인, 전투, 승패, 재도전.
- 저장과 이어하기.

AI 상대는 게임 규칙에 따라 동작하는 C# 로직으로 구현한다.
플레이 중 생성형 AI API 호출을 필수로 만들지 않는다.

## 구현과 연출

전투 규칙은 화면과 독립적인 순수 C# 영역으로 만든다.
카드 효과는 일정한 처리 순서를 따르고, 실제 판정 기록을 UI와 연출이 함께 사용하도록 한다.

확률 판정에는 저장·복원이 가능한 난수 상태를 사용한다.
같은 초기 상태, 난수 상태, 행동에서는 같은 결과가 나와야 한다.
코인 애니메이션을 재생하면서 새로운 판정 난수를 뽑지 않는다.

카드 선택, 확대, 배치 가능 위치, 공격 대상, 방어 대응, 현재 단계와 자원 상태가 명확하게 보이게 한다.
코인 결과와 능력치 변화, 피해 계산을 이해할 수 있게 보여준다.
효과가 재생되는 동안 중복 입력으로 같은 행동이 두 번 실행되지 않게 한다.

아트는 기존에 승인한 판타지 일러스트의 분위기를 기준으로 삼는다.
카드 원화, 프레임, 이름, 수치, 설명은 분리한다.
작은 크기의 카드에서도 종류·비용·주요 수치가 잘 읽히게 한다.
전장의 입체감, 빛, 카드 움직임, 효과음의 일관성을 다듬는다.

# 5. 게임 B: 새벽의 길

## 목표

예수님과 그 시대를 배경으로 하는 회화풍 반실사 3D 서사 어드벤처를 만든다.

첫 시점은 과거로 이동한 여행자이자 목격자인 플레이어로 정한다.
예수님은 핵심 등장인물이며, 플레이어는 주변 인물과 사건에 참여하고 선택한다.

성경 서술을 따르는 기준 루트와 선택으로 갈라지는 가상 루트를 구성한다.
기준 루트에서 참고한 성경 사건은 출처를 콘텐츠 메타데이터에 기록한다.
창작한 연결 장면과 가상 분기는 구분해 관리한다.

플레이어는 정해진 과거 시점으로 돌아가 다른 선택을 할 수 있다.
이후 새로운 시대와 사건을 장면 단위로 추가할 수 있게 구성한다.

## 시각적 방향

- 기존 예수님 컨셉 원화의 인상과 색감을 참고한다.
- 따뜻한 빛, 자연스러운 얼굴과 인체 비율, 설득력 있는 천과 머리카락 표현.
- 갈릴리 호숫가와 작은 석조 공간을 배경으로 시작한다.
- 캐릭터 한 명과 공간 하나부터 집중적으로 다듬는다.
- 짧은 3인칭 이동과 인물 중심의 대화 카메라를 사용한다.
- 주요 인물의 대기 동작, 시선, 대화 반응을 자연스럽게 연결한다.

기존 고정 자세의 모델은 형태 참고나 임시 에셋으로 사용할 수 있다.
최종 캐릭터에는 모델 정리, 재질, 뼈대와 애니메이션이 필요하다는 점을 작업 목록에 반영한다.

## 첫 플레이 범위

약 5~10분의 시작 구간을 목표로 한다.

- 새 게임, 이어하기, 설정, 타이틀 복귀.
- 짧은 도입 연출과 작은 공간 한 곳.
- 플레이어, 예수님, 보조 인물 한 명.
- 걷기, 카메라 조작, 대화, 사물 조사.
- 의미 있는 선택 두 번.
- 선택에 따라 구별되는 짧은 결과 세 가지.
- 선택 전 체크포인트 두 곳.
- 체크포인트로 돌아가 다른 선택을 시도하는 기능.
- 선택 기록과 발견한 루트를 보여주는 화면.
- 한국어 자막, 글자 크기와 음량 설정.

처음부터 모든 시대와 장대한 분기를 만들지 말고, 위 시작 구간에서 선택과 회귀의 재미를 검증한다.

## 서사와 연출 구현

Ink는 대사, 선택, 조건, 이야기 변수와 분기를 담당한다.
Unity는 이동, 월드 오브젝트, 소지품, UI와 연출을 담당한다.
변수마다 소유하는 시스템을 정하고, 같은 관계나 진행 변수를 독립된 두 사본으로 관리하지 않는다.

공식 Ink Unity Integration을 사용하고 설치 버전의 가져오기 방식과 C# API를 확인한다.
이야기는 편집 가능한 .ink 원문으로 관리한다.

Cinemachine은 플레이와 대화 카메라를 담당한다.
Timeline은 도입부 등의 카메라·동작·음향 연출을 담당한다.
게임의 과거 회귀는 별도의 체크포인트 저장·복원 기능으로 구현한다.

## 과거 회귀와 기억

회귀는 선택지 생성 직전처럼 상태가 안정된 체크포인트를 복구하는 방식으로 구현한다.

체크포인트에는 다음을 함께 저장한다.
- Ink 이야기 상태.
- 장면과 시점 ID.
- 플레이어와 필요한 인물의 위치·상태.
- 월드 오브젝트 상태.
- 소지품과 진행 상태.
- 관계와 이야기 변수.
- 게임 난수 상태.
- 저장 스키마와 스토리 콘텐츠 버전.

이미 발견한 단서와 경험한 루트는 MetaProgress로 분리한다.
현재 세계의 상태는 과거로 돌아가고, 발견한 기억은 유지되는 구조로 만든다.

회귀할 때 진행 중인 Timeline, 오디오, 코루틴과 비동기 연출을 중단한 뒤 상태를 복원한다.
대사 위치만 과거로 바꾸는 것으로 회귀를 처리하지 않는다.
복원 과정에서 보상, 관계 변화나 오브젝트 생성이 중복 적용되지 않게 한다.

새 기억이 선택지를 바꾸는 경우에는 체크포인트 복원 후 MetaProgress를 적용하고 선택지를 다시 생성한다.
이전 분기의 상태가 새로운 분기에 섞이지 않게 한다.

# 6. 공통 아트·저장·빌드 기준

ArtDirection.md에 승인한 원화, 색감, 글꼴, 재질과 조명의 기준을 정리한다.

사용 가능한 이미지 생성 도구와 Blender 작업 환경이 있으면 제작에 활용한다.
에셋 생성 도구가 없으면 기존 에셋으로 가능한 범위를 구현하고, 필요한 에셋의 정확한 사양과 교체 위치를 기록한다.

임시 에셋과 최종 사용 후보를 구분한다.
임시 캐릭터나 회색 상자를 넣은 상태를 최종 비주얼 완성으로 보고하지 않는다.
에셋의 출처와 제작·수정 기록을 함께 관리한다.

저장은 버전이 있는 데이터 형식으로 만든다.
Windows 로컬 저장과 웹 저장을 지원하도록 플랫폼별 처리를 분리한다.
웹 체험판에서 저장을 내보내고 PC에서 가져오는 경로를 준비한다.
불러오기 실패 시 기존 저장을 조용히 덮어쓰지 않게 한다.

각 프로젝트에 Windows용과 웹용 Build Profile을 만든다.
웹용은 로딩 크기, 텍스처, 조명, 그림자와 품질 설정을 별도로 조정한다.
플레이에 필요한 핵심 에셋은 빌드에 포함한다.
Steam 배포는 Windows 빌드를 기반으로 확장할 수 있도록 구성한다.

Windows에서 1080p 기준 60fps를 우선 목표로 삼되, 실제 측정 기기와 결과를 기록한다.
웹에서도 실제 로딩과 입력, 화면 크기, 저장 동작을 확인한다.
측정하지 않은 성능 수치를 달성했다고 보고하지 않는다.

# 7. 작업 순서

M0. 기반 구성
- 환경과 기존 에셋 확인.
- 두 Unity 프로젝트 생성.
- 패키지·버전 고정.
- 기본 씬, UI, 입력, 저장 구조 구성.
- 에디터 실행과 초기 Windows·웹 빌드 확인.

M1. 카드게임 첫 전투
- 규칙표와 카드 데이터.
- 전투 코어와 AI 상대.
- 카드·전장 UI.
- 코인과 전투 연출.
- 승패·재도전·저장까지 연결.

M2. 서사게임 첫 구간
- 캐릭터와 공간.
- 이동·대화·카메라.
- Ink 선택 분기.
- 체크포인트·기억·과거 회귀.
- 결과와 저장·이어하기까지 연결.

M3. 첫 구간 완성도 점검
- 원화와 실제 게임 화면 비교.
- 글자와 UI 가독성.
- 카메라와 애니메이션.
- 효과음과 전환 속도.
- 빌드별 실행과 성능 확인.

각 단계에서 구현한 내용과 남은 문제를 짧게 보고하고, 이번 완료 조건을 향해 계속 진행한다.

# 8. 완료 조건과 보고

카드게임:
- 지형·자원·유닛 배치·방어 대응·코인 판정이 실제로 작동한다.
- 같은 상태와 행동에서 같은 전투 결과가 재현된다.
- 저장 후 불러와도 카드 상태와 다음 확률 판정이 유지된다.
- 승리·패배·재도전까지 실행된다.

서사게임:
- 다른 선택으로 대사, 세계 상태와 결과가 실제로 달라진다.
- 과거 회귀 시 소지품과 관계가 당시 값으로 복원된다.
- 발견한 기억은 유지된다.
- 회귀와 다른 선택을 반복해도 이전 분기의 상태가 섞이지 않는다.
- 종료 후 다시 실행하여 이어할 수 있다.

공통:
- 중요한 전투 규칙과 회귀·저장 동작에 자동 테스트를 작성한다.
- 실제 Unity 실행 화면과 가능한 빌드에서 조작을 검증한다.
- 생성한 씬과 프리팹, 에셋 연결에 누락이 없는지 확인한다.
- 실제 화면 캡처와 Windows·웹 빌드 결과물을 제공한다.
- 테스트하지 못한 항목은 실행했다고 주장하지 않고 구분한다.
- 실행 방법, 검증 결과, 임시 에셋, 남은 작업을 정리한다.

이제 현재 작업 폴더와 실행 환경을 확인하고 M0부터 실제 작업을 시작해라.
